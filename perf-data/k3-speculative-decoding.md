# Speculative decoding for K3: benched, and it does not pay. Three independent reasons.

**Measured 2026-07-31**, branch `k3-batched-decode`. This closes the campaign's last open clause —
"speed bench with speculative decoding" — with a NEGATIVE result, and the negative result is the
deliverable rather than a deferral.

## 0a. SCOPE DECISION, confirmed by the user 2026-07-31

Speculative decoding is **deliberately out of scope for this campaign**, confirmed explicitly when
the conflict was put to the user: the campaign goal text names it, and the user's instruction was
*"ignore speculative decoding path, focus only on improving the current path."* Asked directly to
choose, they chose to keep it descoped.

So this document is the DELIVERABLE for that clause, not a placeholder for one. The bench was run,
the numbers are below, and the answer is that it loses on this model by 3-5x for reasons that are
structural rather than implementation quality. §5 records exactly what would have to change first.

## 0. What was actually available to bench

Speculative decoding needs a draft. K3 has none:

* **No draft checkpoint.** K3 is 93 layers / 69 KDA + 24 MLA. There is no smaller sibling in the
  tree and no second checkpoint on this box.
* **No trained heads.** EAGLE / Medusa need heads trained against this target. They do not exist.
* **`crates/plowrt/src/orch/speculative.rs` is a design sketch, not an implementation** — 150 lines
  of `accepted_prefix`, `committed_tokens` and a config struct, with **zero references anywhere
  else in the tree** (grepped). Nothing calls it.

That leaves exactly one variant that needs no draft model: **n-gram / prompt-lookup speculation**
(propose the continuation that followed the most recent match of the last N tokens). So that is
what was benched.

## 1. ACCEPTANCE IS ~ZERO — measured on REAL K3 TOKEN IDS

The load-bearing number, so it was measured twice: once at word granularity on GSM8K reference
text, and once on **400 real token ids generated by K3 itself** (`amd-bench --tp 8 --steps 400`,
prompt `1008,10484,318,15383,387`, the README's known-good continuation). Real tokens are the
stronger measurement and they are WORSE:

| lookup | mean accepted | tokens per verify step | full-accept |
|---|--:|--:|--:|
| N=1, K=4 | **0.08** | **1.08** | 0% |
| N=2, K=4 | 0.04 | 1.04 | 0% |
| N=2, K=8 | 0.04 | 1.04 | 0% |
| N=3, K=4 | 0.01 | 1.01 | 0% |
| N=3, K=8 | 0.01 | 1.01 | 0% |

**Zero full-accepts in 400 tokens at any (N, K).**

### The break-even, stated so it can be checked

A verify step wins only if it costs less than `(1 + mean_accepted)` decode steps. At the MEASURED
29.0 ms decode step:

| mean accepted | verify budget | actual verify cost |
|---|--:|--:|
| **0.08 (measured)** | **31.3 ms** | **~100-150 ms** (§2) |
| 0.5 | 43.5 ms | ~100-150 ms |
| 1.0 | 58.0 ms | ~100-150 ms |
| 2.0 | 87.0 ms | ~100-150 ms |

It loses by **3-5x at the measured acceptance**, and it would still lose at an acceptance of 2.0
tokens per step — which is 25x what was measured. The verify budget cannot be met by tuning,
because a verify pass runs k+1 rows through all 93 layers plus k+1 lm_heads; it cannot be cheaper
than a decode step, and break-even needs it to be barely more than one.

## 1b. The word-granularity cross-check (GSM8K)

Simulated over GSM8K 8-shot, 50 questions, prompt + reference chain-of-thought (the same
distribution the model emits), at WORD granularity — an ESTIMATE, and if anything a generous one,
since a matched word is 1-2 BPE tokens:

| lookup | mean accepted | tokens per verify step | full-accept rate |
|---|--:|--:|--:|
| N=2, K=4 | 0.12 | **1.12** | 1% |
| N=3, K=4 | 0.04 | 1.04 | 0% |
| N=3, K=8 | 0.05 | 1.05 | 0% |
| N=4, K=8 | 0.02 | 1.02 | 0% |

Best case **1.12 tokens per step, i.e. a 10% GROSS saving before a single cost is charged.**
Chain-of-thought arithmetic is not extractive — it does not copy long spans out of its own context
the way summarisation or code editing does, which is the regime prompt-lookup is built for.

## 2. THE VERIFY STEP COSTS ~4-5x A DECODE STEP, because the smallest bucket is 128 rows

This is the structural one, and it is specific to plow rather than to speculation.

Verification runs the target over the k proposed tokens in one pass — which on this runtime means
the PREFILL program. The compiled bucket ladder is `[128, 512, 1024, 2048, 4096, 8192]`
(`mla.rs`), so **verifying k=4 tokens executes a 128-row bucket: 32x more rows than needed.** There
is no smaller rung and adding one is its own emit + object + tuning exercise.

DERIVED from the prefix-cache A/B (GSM8K B=1 CONC=1, median 4.88 s/question cold vs 3.70 s on a
cache hit that skips ~1037 prompt tokens): a 1152-row cover costs ~1.18 s, so a 128-row chunk is
order **100-150 ms** — against a **29.0 ms** decode step (MEASURED). A verify step therefore costs
roughly **4-5x a decode step and returns 1.12 tokens.**

Even at 100% acceptance with k=4 it would be a wash; at the measured acceptance it is a 4x loss.

## 3. K3's RECURRENCE CANNOT BE REWOUND, so every rejection pays a rollback

The reason speculation is structurally worse for this model than for a pure-attention one.

A rejected token's KV is harmless — it is overwritten, and `kvlen` bounds every read. **The KDA
recurrence is not.** `d_kda_state_step_t` reads and writes `state[row]` for every row it runs, so
after verifying k tokens the recurrence has absorbed all k, including the rejected ones. There is
no inverse.

The only fix is snapshot-before-verify / restore-on-rejection, and this campaign already built and
MEASURED that machinery for the prefix cache: **3.67 ms per restore per rank**
(`crates/plowrt/src/obs/pfx.rs`, `PLOW_PFX_LOG=1`). At the measured ~99% rejection rate that is a
per-step tax on essentially every step, on top of §2 — plus a re-run of the accepted prefix, which
gives back the saving that motivated the whole thing.

## 4. And it cannot help the goal that was actually set

The campaign target was resolved to **aggregate** throughput, not per-stream latency. Speculative
decoding trades compute for latency: it does more FLOPs per committed token in exchange for fewer
sequential steps. At B=16 the machine is already saturated (MEASURED 91.3 tok/s aggregate), so
there is no idle compute for speculation to spend, and it **cannot raise aggregate throughput at
all**. It is a single-stream latency technique.

## 5. What would change this answer

Stated so the conclusion is falsifiable rather than final:

1. **A real draft model** — a small dense checkpoint sharing K3's tokenizer. Acceptance would come
   from a model rather than from string matching, and 60-80% is the usual regime. §2 and §3 still
   apply and still have to be paid.
2. **A prefill bucket smaller than 128** (say 8 or 16 rows), which would cut §2 from 4-5x a decode
   step to something near 1x. This is worth doing on its own merits for short prompts, independent
   of speculation.
3. **An extractive workload** — summarisation, RAG, code editing — where prompt-lookup acceptance
   is genuinely high. The measurement in §1 is specific to GSM8K chain-of-thought and should be
   re-run per workload rather than assumed.

Items 1 and 2 are prerequisites, not optimisations: with acceptance at 0.12 and a 4-5x verify cost,
no amount of implementation quality makes this profitable.
