# Gemma-4-12B on a sandbox RTX 5090 — a real prefill-blocking bug, a fixed
# vLLM bug, and the first live same-box comparison

2026-08-25 · RTX 5090 (sm_120a, 170 SMs, 32 GB GDDR7) · driver 580.65.06 · CUDA 13.0 (system
nvcc, outside `nix develop` per this repo's own convention) · nix 2.35.2 (single-user install,
`/nix` on the box's own root filesystem — the sandbox's `mount` syscall is unavailable, so the
usual bind-mount-to-a-bigger-disk trick used elsewhere in this repo could not be applied) ·
`google/gemma-4-12B-it` (dense, 48 layers / 40 sliding + 8 full, hd 256/512, kvh 8/1,
`attention_k_eq_v=true`) · vLLM 0.27.0 (flake-pinned, pip-installed into a venv, run with a
source-level patch — see §3).

This is a fresh sandbox, not a continuation of the gh200/H100/5090 boxes behind the other
`gemma4-12b-*.md` files in this directory. Nothing here should be read as superseding those —
it is an independent data point, with its own bring-up story, on different physical hardware.

## Summary

- **A real, previously-undocumented bug blocked ALL prefill serving on `main`** for the sm_120a
  `--hf-dir` path: `PLOW_UNISEG=1` is required and not defaulted or enforced. Fixed by passing
  it explicitly at every compile in this report. See §1.
- **`GV_MM_MAX=16` is a clean, register-neutral decode win at every concurrency tested**
  (c1 through c16, +15-29%). See §2.
- **vLLM 0.27.0 could not serve `google/gemma-4-12B-it` at all, out of the box, in this
  environment** — three independent bugs, hit in sequence. Two were workaroundable from outside
  vLLM's source. The third — every full-attention layer's `q_norm`/`k_norm` allocated at the
  wrong (sliding) head_dim, a version-skew bug between vLLM 0.27.0's `gemma4.py` and the paired
  `transformers` 5.15.1 release's new heterogeneous-config schema — was fully root-caused **and
  fixed**, in-process, without editing the installed packages. See §3.
- **With vLLM actually running, a live, same-box, same-protocol, same-client comparison was
  obtained for the first time in this report.** Headline: **vLLM currently wins at every
  concurrency and every context length tested — decode by 33-37%, prefill by 39-59% — even
  after the `GV_MM_MAX=16` win.** See §5. This is the load-bearing result of this report; §2's
  and §4's isolated plow numbers should be read in light of it, not as wins in themselves.

## 0. Environment bring-up notes (for the next person on a similarly locked-down sandbox)

- `mount` is unavailable (returns a bare "permission denied" for both a fresh directory and a
  symlink target — looks like a seccomp restriction, not a capability gap: `id` shows `uid=0`).
  The usual "put `/nix` on the big disk" trick doesn't work here. Nix went on `/` (only 40 GB)
  instead; model weights, venvs, and build artifacts went on `/workspace` (100 GB). This fit
  comfortably (`/nix` ended up ~7 GB) but would not scale to a campaign needing the AMD/ROCm
  toolchain (a much larger closure) — not needed here since no AMD GPU exists in this sandbox.
- `nix develop`'s default devShell unconditionally includes `gpu.rocm` on `x86_64-linux`
  (`flake.nix:344-364`) even though nothing here targets AMD. Avoided entirely: `nix build
  .#plowc .#plowrt .#plow-interp-sm120a` instead of `nix develop`, which only touches
  `gpu.cudatoolkit`. `plowc`/`plowrt` are pure-Rust `buildRustPackage` derivations with no GPU
  toolchain dependency at all. `plow-interp-sm120a`'s nix derivation already builds with
  `-DPLOW_FP8_KV_FASTPF=ON` by default (`flake.nix:289-293`) — convenient, matches the intended
  production config. `cargo build --release -p plowrt --features cuda --example step_bench` and
  the two `tunedb` binaries were built the same way, via `nix shell nixpkgs#cargo
  nixpkgs#rustc nixpkgs#gcc` rather than `nix develop`.
- Single-user nix-as-root needs a `nixbld` group with at least one **non-root** member (`useradd
  -r -g nixbld -G nixbld nixbld1`); root itself must NOT be a member of `nixbld` (the installer
  explicitly rejects that combination). Not documented anywhere in this repo; recorded here in
  case another sandboxed environment hits it.
- `pkill -f "<substring>"` matches the pkill invocation's OWN command line if that command line
  contains the pattern text (which it always does, verbatim, as an argument) — killed the
  invoking shell itself repeatedly before switching to `pkill -x <exact-process-name>` (still not
  perfectly safe — `pkill -f vllm_launch.py` still self-matches since the pattern text is part
  of the very command being run). Cost real time before the cause was obvious; worth a note in
  any future tooling here that shells out to `pkill -f`.
- `scripts/tune_decode_sweep.sh` and the documented `nix develop` / `gpulease` workflow assume a
  standard multi-GPU dev box; adapting its cross-toolchain orchestration to this one-off sandbox
  (no `gpulease`, one GPU, no daemon) was not attempted. The tuning result in §2 was obtained by
  a direct, manual before/after `cuobjdump`+bench A/B instead — faster for a single targeted
  knob, but it is not a substitute for populating `tunedb` with a qualified record, and doesn't
  scale to a real multi-knob sweep.
- The `google/gemma-4-12B-it` checkpoint ships one unsharded 23.9 GiB `model.safetensors`
  matching `devgen/src/checkpoint.rs`'s documented single-shard handling, `config.json`
  `model_type: "gemma4_unified"` with a nested `text_config` (`head_dim=256`,
  `global_head_dim=512`, `attention_k_eq_v=true`, `layer_types` alternating with full-attention
  at indices `[5, 11, 17, 23, 29, 35, 41, 47]`) — matches `hf_config.rs`'s `synth_gemma` path
  exactly, no code changes needed.
- fp8 weight quantization used `perf-data/tools/quantize_fp8.py` directly against the vLLM
  venv's torch (2.13.0) rather than the `nix develop .#quantize` shell — same RTN/e4m3
  per-output-channel method the script documents, just a different torch source; took 38 s for
  the full 328-projection sweep. `plowrt --fp8-dir` turned out to be **AMD-only**
  (`crates/plowrt/src/exec/amd.rs`; not read by `exec/gpu.rs` at all) — the working pattern on
  NVIDIA is a checkpoint directory holding both the original `model.safetensors` and the fp8
  twins file as siblings (`Checkpoint::open` unions every `*.safetensors` in the directory by
  tensor name), passed via `--rt-checkpoint`. Worth promoting to a `--fp8-dir`-equivalent on the
  CUDA path, or at minimum documenting, since the current failure mode (`MISSING WEIGHT:
  fp8/model...`) gives no hint that the flag is backend-specific.

## 1. Prefill-serving bug (Phase 0 critical check)

`perf-data/px23-hd256-fp8-prefill.md` recorded, on 2026-07-26, that prefill serving of this exact
model was broken on `main` independent of PX-23's own change — even a 20-word bf16 prompt failed
with `CUDA_ERROR_LAUNCH_FAILED`, and flagged re-verifying this as the single blocking item before
anything else in that campaign could proceed.

Reproducing that check here: `plowc --hf-dir ... --arch sm_120a --gpu rtx5090` (no `--uniseg`)
compiles without error, but `plowrt serve` refuses to load the resulting asset:

```
Error: Msg("gemma-4-12b-it: model load failed: device error: prefill object ...
failed to load: device error: devblob: prog T=128 stream entry 6 is segmented/fine-gated;
the sm_120 interpreter implements the coarse single-segment path only
Refusing to start: falling back to decode-only prompt consumption would prefill one token
at a time (measured >=707 s vs ~32 s on a 127k prompt) with no symptom but slowness.")
```

This is `crates/plowrt/src/asset/devblob.rs`'s `check_coarse_single_segment` gate — it is working
exactly as designed (refuse rather than silently degrade to token-at-a-time prefill). The fix:
`PLOW_UNISEG=1` (an environment variable — the CLI's `--uniseg` flag sets a **different** field
that only feeds a diagnostic warning; the actual gate in `packet::devbuild::Builder` at
`crates/packet/src/devbuild.rs:1117-1118` reads `std::env::var("PLOW_UNISEG")` directly, not the
parsed `EmitConfig`). With the env var set, `plowc --uniseg`'s own help text says this plainly
("Required for sm_120 prefill interpreter") — but nothing in the `--hf-dir` path enforces or
defaults it, so a plain README-quickstart invocation on sm_120 silently produces an asset that
cannot serve prefill at all.

**Verified fixed** (i.e., PX-23's finding does not reproduce as a code defect on this box's
`main`): with `PLOW_UNISEG=1`, `plowrt serve` loads, and both a 25-token and a 149-token
prefill+decode round trip through `/v1/chat/completions` return correct, coherent output
("Paris"; a correct explanation of bicycle stability). This was re-verified again after every
subsequent cubin/asset change in this report.

**Open item**: `--hf-dir --arch sm_120a` should either default `PLOW_UNISEG=1` or `plowc` should
refuse to emit a segmented sm_120 asset the way `plowrt` refuses to load one — right now the
failure is deferred from compile time to serve time, on a different binary, with a message that
doesn't name the missing flag.

## 2. Decode-side tuning: `GV_MM_MAX=16`

Setup: `plowc --hf-dir ... --emit-decode-batch-ladder 1,4,8,16 --max-ctx 2048`, fp8 weights
(w8a16 — needed to fit the batch-16 KV cache: bf16 weights + the ladder's batch-16-sized KV
cache is ~33 GiB, over the ~31.4 GiB usable on a 32 GB card; fp8 weights bring it to ~22.8 GiB).
`PLOW_DEV_SAMPLE=1 PLOW_MULTISTEP=8` on throughout (both known-good from prior campaigns,
applied at compile time here rather than swept). Client: `vllm bench serve --backend
openai-chat`, `--random-input-len 128 --random-output-len 1024 --ignore-eos`, matching
`gemma4-12b-sm120-serving.md`'s protocol. Correctness gated before every timed run (greedy
"Paris" + a longer coherent-paragraph check).

The shipped default is `GV_MM_MAX=8` (`gemv_weight_passes=2` at batch 16 — a decode-batch-16
step re-reads its weight tile twice). Rebuilt the interpreter object with
`PLOW_EXTRA_DEFINES="-DGV_MM_MAX=16"` via `scripts/build_sm120_cubin.sh` (system nvcc, outside
`nix develop`, per this repo's convention) — `gemv_weight_passes` drops to 1.

| concurrency | MM=8 (tok/s) | MM=16 (tok/s) | delta |
|---|---|---|---|
| 1  | 31.70  | 38.41  | **+21.2%** |
| 4  | 106.18 | 136.51 | **+28.6%** |
| 8  | 217.35 | 250.50 | **+15.3%** |
| 16 | 417.56 | 489.84 | **+17.3%** |

`cuobjdump -res-usage` on the persistent interpreter kernel is byte-identical between the two
builds (`REG:255 STACK:1024 SHARED:3216 LOCAL:0` both) — the win costs nothing in register
pressure or spilling. Coherence re-checked after rebuilding (same two prompts, same correct
output).

**This contradicts `tuning/README-decode-tuner.md`'s own documented finding** ("at B=8, `=8`
beats `=16` by 34.8%", from `perf-data/px15-tunedb-sm120.md` on a different physical box). Ran a
direct bf16-vs-fp8 isolation to check whether that was a precision artifact of running fp8 here:
compiled a second, bf16 asset (ladder capped at batch 8, since bf16+ladder-16 doesn't fit VRAM)
with the same `GV_MM_MAX=16` object. bf16 was **slightly slower** than fp8 at every point tested
(c1: 36.47 vs 38.41; c4: 126.91 vs 136.51; c8: 240.13 vs 250.50) — consistent with this decode
path being HBM-bandwidth-bound rather than dequant-compute-bound, and ruling out precision as
the explanation for the MM=16 discrepancy with the prior doc. The discrepancy is unresolved;
plausible causes not yet checked: different `GV_UNROLL`/`PLOW_NS_ABS` defaults between the two
builds, a different context length in the prior sweep, or a genuinely different regime on
different hardware. **Do not treat px15's B=8 finding as current without re-checking it
directly** — this report's own B=8 number moved the other direction.

No `tunedb` record was written for this — it's a hand rebuilt-and-measured A/B, not a qualified
measurement through `tunedb-decode ingest`. `tuning/nvidia/sm_120a/rtx-5090/decode_measurement.jsonl`
still has no batch=16 cell and reflects the *other* physical 5090 this repo's tuning data was
collected on, not this sandbox. **This win, alone, does not close the gap to vLLM — see §5.**

## 3. vLLM 0.27.0: three bugs, two workarounds, one real fix

Attempting `vllm serve google/gemma-4-12B-it` (venv-installed 0.27.0, matching the flake pin)
failed in sequence on three independent defects, none plow-side.

### 3.1 `transformers` heterogeneous-config strictness (worked around)

`vllm/transformers_utils/model_arch_config_convertor.py` reads `hf_text_config.head_dim` as a
plain global attribute before any `--hf-overrides` reach the nested `text_config` object;
`transformers.integrations.heterogeneity` raises `AmbiguousGlobalPerLayerAttributeError` because
Gemma-4's `head_dim` genuinely does vary by layer (256 sliding / 512 full).
`--hf-overrides '{"allow_global_per_layer_attribute_access": true}'` does not reach the nested
object either. Worked around with an in-process monkeypatch
(`HeterogeneousConfigMixin.allow_global_per_layer_attribute_access` defaults `True`) from a
launcher script — no edit to the installed package.

### 3.2 `flashinfer`'s Python-version-incompatible type annotation (worked around)

`comm/fd_exchange.py`: `def _fd_ancillary(fd: int) -> tuple[tuple[int, int, array.array[int]]]:`
— `array.array` doesn't support `__class_getitem__` (subscripting) before Python 3.13; this venv
runs 3.11. The annotation is evaluated eagerly at import time (no `from __future__ import
annotations` in that file), so importing `flashinfer.comm` — pulled in unconditionally by vLLM's
allreduce-fusion compilation pass, even at TP=1 where no inter-GPU exchange ever runs — raised
`TypeError: type 'array.array' is not subscriptable` before the server could resolve the model
architecture. Worked around by pre-registering a stub module in `sys.modules` for
`flashinfer.comm.fd_exchange` (its two exports, `broadcast_fd`/`exchange_fds`, both replaced with
a function that raises if ever actually called — never happens at TP=1).

### 3.3 Full-attention-layer norm sizing bug (root-caused AND fixed)

Every full-attention layer's `q_norm.weight`/`k_norm.weight` was allocated at the *sliding*
head_dim (256) instead of the *full* head_dim (512). Root-caused with a diagnostic wrapper around
`default_weight_loader` that reports the failing parameter name via a stack-frame inspection: the
first failure is `layers.11.self_attn.k_norm.weight`, `param.size()=(256,)
loaded_weight.size()=(512,)`. Layer 11 is not special — the checkpoint's raw tensor order is
lexicographic (`layers.0, layers.1, layers.10, layers.11, ...`), and layer 11 is simply the
*first* full-attention layer (of `[5, 11, 17, 23, 29, 35, 41, 47]`) reached in that order.

`Gemma4DecoderLayer.__init__` reads `getattr(config, "global_head_dim", config.head_dim)` for
full-attention layers (`gemma4.py:576`; `num_global_key_value_heads` similarly at line ~589).
`config` is the same shared object across every layer (captured once by `make_layers`'s lambda
closure), so a per-layer-view theory was ruled out directly: `AutoConfig.from_pretrained(...).
get_text_config()` on this checkpoint confirms `hasattr(tc, "global_head_dim")` is **False** —
`Gemma4UnifiedTextConfig` (the class transformers 5.15.1 actually instantiates for this
checkpoint) does not define that field at all. transformers moved Gemma-4's config to the new
heterogeneous per-layer system (`per_layer_attributes = {'head_dim', 'num_key_value_heads'}`,
accessed via `config.per_layer_config[i]`) and dropped the legacy flat `global_head_dim` /
`num_global_key_value_heads` fields vLLM's `gemma4.py` still reads. The `getattr` therefore always
silently falls through to its default (`config.head_dim`, the sliding value) on every access,
for every full-attention layer — a version-skew bug between vLLM 0.27.0's Gemma4 support and the
paired transformers release in this environment, not anything to do with plow, the checkpoint, or
this sandbox.

**Fixed**, from the launcher script, without editing either installed package: added
`global_head_dim` / `num_global_key_value_heads` as properties on `Gemma4UnifiedTextConfig` that
look up the first full-attention layer's values from `per_layer_config` (uniform across all 8
full-attention layers in this architecture — confirmed `per_layer_config[5].head_dim == 512`,
`.num_key_value_heads == 1` directly before wiring the fix in):

```python
def _first_full_attn_layer_config(self):
    idx = self.layer_types.index("full_attention")
    return self.per_layer_config[idx]

Gemma4UnifiedTextConfig.global_head_dim = property(
    lambda self: _first_full_attn_layer_config(self).head_dim)
Gemma4UnifiedTextConfig.num_global_key_value_heads = property(
    lambda self: _first_full_attn_layer_config(self).num_key_value_heads)
```

With all three patches applied (`/workspace/plow-work/vllm_launch.py` — a drop-in wrapper for
`python -m vllm ...` / `vllm serve ...`, not a fork of vLLM), `vllm serve` loads the full model,
completes `torch.compile` + CUDA-graph capture (PIECEWISE + FULL), and serves correct, coherent
output — same two prompts as plow's own gate ("Paris"; the bicycle-balance explanation, near-
verbatim in content to plow's own answer).

This bug is real and should be reported upstream (vLLM's `gemma4.py`, or transformers'
`Gemma4UnifiedTextConfig`, depending on which project considers itself the source of truth for
the legacy field names) — as shipped, `google/gemma-4-12B-it` cannot be served on vLLM 0.27.0 +
transformers 5.15.1 without a source-level patch. The `qkv_proj` (2-D) weights for the same
layers loaded without error even before this fix, which remains unexplained — plausibly
`QKVParallelLinear`'s stacked-shard loading path validates size differently than
`default_weight_loader`'s plain per-tensor assert; not investigated further since it's moot once
the actual head_dim resolution is fixed.

## 4. Prefill: plow's own numbers

Setup: `plowc --hf-dir ... --max-ctx 16384 --batch 1`, bf16 weights, the original nix-built
cubin (`-DPLOW_FP8_KV_FASTPF=ON`, matching production defaults — this report's own
`GV_MM_MAX=16` rebuild did not carry FASTPF forward since it only touched nvcc-level defines, not
the cmake-level FASTPF option; the two rebuilds in this report are independent one-knob-at-a-time
changes, not a combined build). `--seq` does not control the emitted prefill bucket ladder for
the `--hf-dir` path (stayed at the devgen-internal default `[128, 512, 1024]` regardless of the
value passed) — longer prompts are served by chunking through that fixed ladder, not by a wider
compiled bucket. Concurrency 1, `--random-output-len 8` (isolates prefill; TTFT ≈ full-prompt
prefill wall time at concurrency 1).

| input length | TTFT (ms) | implied tok/s |
|---|---|---|
| 2,048  | 464.0  | ~4,414 |
| 8,192  | 1,729.4 | ~4,738 |
| 16,000 | 3,494.3 | ~4,579 |

Roughly flat ~4,400-4,700 tok/s across this range (expected — the quadratic attention term is
still small relative to the linear GEMM term at ≤16k tokens on this model).

No prefill-side tuning (FASTPF on/off A/B, `PLOW_NV_FA_FP8PV`, the segmented-GEMM-reachability
item) was attempted in this report — see Open Items. **These numbers, on their own, are not
competitive with vLLM on this box — see §5.**

## 5. The live, same-box comparison

With §3's fix in place, vLLM was run on the identical box, identical client
(`vllm bench serve --backend openai-chat`), identical dataset shapes, identical concurrency
values as plow's own §2/§4 sweeps. vLLM: bf16 (no quantization flags passed — matches the
checkpoint's native dtype), `--gpu-memory-utilization 0.93` for the decode sweep (KV pool 17,100
tokens — fits ~14-15 of the 1,152-token decode requests simultaneously, slightly under a full
c16; `--max-model-len 17000` for the prefill sweep, `0.90` utilization, no queuing observed at
any point). 0 failed requests at every concurrency and every context length on both engines —
both comparisons are clean, no errors or timeouts to caveat.

**Decode** (128 in / 1024 out, `--ignore-eos`):

| concurrency | plow, fp8, GV_MM_MAX=16 (tok/s) | vLLM 0.27.0, bf16 (tok/s) | plow/vLLM |
|---|---|---|---|
| 1  | 38.41  | 57.55  | 0.67x |
| 4  | 136.51 | 215.64 | 0.63x |
| 8  | 250.50 | 397.77 | 0.63x |
| 16 | 489.84 | 735.23 | 0.67x |

**Prefill** (concurrency 1, output-len 8, TTFT-derived tok/s):

| input length | plow, bf16 (tok/s) | vLLM 0.27.0, bf16 (tok/s) | plow/vLLM |
|---|---|---|---|
| 2,048  | 4,414 | 7,027 | 0.63x |
| 8,192  | 4,738 | 6,819 | 0.69x |
| 16,000 | 4,579 | 6,376 | 0.72x |

**vLLM wins every single point in both tables, by a fairly consistent ~30-40% on decode and a
narrowing (but still substantial) 28-37% on prefill as context grows.** The decode gap is
essentially unchanged in relative terms by the `GV_MM_MAX=16` win — it moved plow's absolute
numbers up 15-29% (§2) but vLLM's absolute numbers are far enough ahead that the ratio barely
shifted. This matches this report's own earlier discovery in §2 that plow's current decode path
is HBM-bandwidth-bound: the fix that's actually needed is the batched-decode-GEMV kernel
redesign flagged as the "harder lever" in this campaign's plan (wider weight-tile residency
across the batch, closing the redundant-HBM-read gap directly) — not further knob-tuning of the
existing kernel, which this section's own MM=16 result suggests is close to exhausted as a lever.

**This is the honest headline of this report: on this box, with the tuning applied so far,
plow does not beat vLLM at any tested point, on either prefill or decode.** The `c16` decode
crossover this repo's other `gemma4-12b-sm120-serving.md` documented on a *different* physical
5090 (plow tying/beating vLLM at c4/c8, losing only at c16) does not reproduce here even
directionally — this box's plow numbers trail vLLM at every concurrency including c1 and c4.
Given §2 already ruled out precision (fp8 vs bf16) as the explanation and confirmed no
register/occupancy regression from the applied tuning, the most likely explanation is that this
sandbox's plow build is missing several of the *other* already-known-good levers the other box's
campaign applied cumulatively (this report applied only `GV_MM_MAX`, `PLOW_DEV_SAMPLE`, and
`PLOW_MULTISTEP` — not `PLOW_NS_FULL_ABS` tuning, tunedb calibration, or the deeper GEMV redesign)
— not a hardware or methodology difference. **Closing this gap is unfinished work, not a
contradiction to resolve.**

## 6. What this report does and does not claim

- **Does claim**: prefill serving works on this box once `PLOW_UNISEG=1` is set (§1); a specific,
  validated, register-neutral decode win of +15-29% from `GV_MM_MAX=16` across concurrency 1-16
  (§2); a live prefill baseline at three context lengths (§4); a real vLLM 0.27.0 bug, fully
  root-caused and fixed without editing installed packages, that otherwise makes this model
  unservable on vLLM at all in this environment (§3); and a clean, same-box, same-protocol,
  zero-failed-requests comparison at every tested point (§5).
- **Does not claim**: a "beats vLLM" verdict at any concurrency or context length tested. §5's
  numbers are the honest result: vLLM currently wins everywhere measured here. The gap is
  quantified precisely enough to prioritize the next round of work (§2's kernel-redesign
  pointer, §7's open items) rather than guess at it.

## 7. Open items, in priority order

1. **The batched-decode-GEMV kernel redesign** (this campaign's plan flagged this as the "harder
   lever" if config tuning proved insufficient — §5 confirms it is). `GV_MM_MAX=16` alone leaves
   a ~35% gap essentially unmoved in relative terms; closing it needs the weight-tile-residency
   work itself, not another knob.
2. **Report the vLLM/`transformers` version-skew bug upstream** (§3.3) — `vllm/model_executor/
   models/gemma4.py`'s `global_head_dim`/`num_global_key_value_heads` reads against
   `Gemma4UnifiedTextConfig`, which no longer defines those fields under the new heterogeneous
   config system. This affects anyone trying to serve `google/gemma-4-12B-it` (or any Gemma-4
   variant with heterogeneous per-layer attention) on this vLLM/transformers pairing.
3. **`--hf-dir --arch sm_120a` should default or enforce `PLOW_UNISEG=1`** (§1) — a
   straight-from-README compile currently produces an asset that fails at serve time with a
   message that doesn't name the missing flag.
4. **Reconcile the `GV_MM_MAX=16` B=8 discrepancy with `px15-tunedb-sm120.md`** (§2) — re-run
   both builds' full knob set (`GV_UNROLL`, `PLOW_NS_ABS`) side by side rather than isolating
   `GV_MM_MAX` alone, since an interaction with a differing default is the most likely explanation.
5. **Populate `tunedb`** for this box's `gemma-4-12B-it`/sm_120a/rtx-5090 cell properly (this
   report's win was a hand A/B, not a qualified `tunedb-decode` record) so kernel selection stops
   falling back to the analytical/portable tier — and apply the other already-known-good levers
   from the other 5090's campaign (`PLOW_NS_FULL_ABS` tuning in particular) that this report did
   not carry over.
6. **Prefill-side tuning was not attempted here**: FASTPF on/off A/B on this box specifically
   (now directly comparable to a live vLLM baseline, unlike prior campaigns), `PLOW_NV_FA_FP8PV`,
   and the `PLOW_NV_SEG_GEMM`/`PLOW_UNISEG` reachability tension noted in
   `gemma4-12b-longctx-5090.md` §6 all remain open — and now, unlike before, can be measured
