# gfx950 decode GEMV_GLU at K=7168: UN=7 unroll rung

Date 2026-09-04. Kimi-K3, 8x MI355X, TP8, BF16 KV. Same control packet (`f1bf783d…`, measured
7,650/7,650 tiles), two packet-paired object sets that differ only in `d_gemv_glu`
(`runtime/amd/op_gemm.h`): the shared-expert gate/up GEMV (N=768 per rank, K=7168, 92 packets
per token) used the generic `GV_UNROLL_GLU=6` chunk unroll, which for the 14 chunks of K=7168
runs three passes with four dead loads; `d_gemv_qkvg` already takes a `K == 7168 → UN=7` rung
(two clean passes, measured 13% faster on its shape). This adds the same rung to `d_gemv_glu`.
Per-lane accumulation order is unchanged (chunks still visit k in order), so outputs are
bit-identical.

Trace motivation (one-token decode trace of the current default, `/tmp/k3-xr-phase-gate/
trace-ctl.report`): `GEMV_GLU` b=256, 92 packets, 10.4 µs body each, with 3 of 8 waves busy
(3 rows per workgroup) and a 38.5 µs max-min workgroup-end spread.

Resources: decode gq object unchanged at 248 VGPR / 106 SGPR / 84 SGPR spills / 216 B private /
occupancy 2 (`.text` +6.4 KB). Runtime `--amd-tp-no-audit`, compact audit, one warm-up, three
8192→256 requests per fold, order-alternated g/c/c/g/g/c under an exclusive `gpulease -n 8`.

| fold | control TPOT p50 | UN=7 TPOT p50 |
|---|---:|---:|
| 1 | 28.605 ms | 28.500 ms |

All six folds produced the identical 256-token checksum `fnv1a64:b7682a38c151ac99`; TTFT
unchanged (1262-1263 ms).

## Decision

Promote (interpreter arm, no flag: the rung is a runtime `K == 7168` branch like the QKVG one).
Because it changes kernel source, the gfx950 TuneDB implementation digest moves; a packet
emitted from this source is gate-valid only after the dense-GEMM requalification campaign
(`scripts/rebench_tune_gemm_all.sh`) re-measures the 7,650 tiles under the new label. This A/B
avoided that by pairing the unchanged control packet with objects built from the new source.

## Next on this family

The remaining GLU cost is the idle-wave split (3 of 8 waves per workgroup) and the 38 µs tail,
not the unroll; a row-per-wave split across two workgroups per row group, or folding the shared
GLU into the adjacent GEMV packet, is the next candidate.
