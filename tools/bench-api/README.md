# bench-api

Realistic-workload latency/throughput harness for OpenAI-compatible servers
(`plowrt serve`, `vllm serve`). Python 3 stdlib only; `tokenizers` optional.

Files:

- `bench.py` — drives streaming `/v1/chat/completions`, writes `results.json` + `results.md`.
- `corpus.py` — deterministic prompt generator (original prose; seed-stable).
- `compare.py` — side-by-side markdown table from two `results.json`.

## Usage

```
python3 tools/bench-api/bench.py \
  --base-url http://localhost:8093 --model <id from /v1/models> \
  --workload chat_short|chat_long|rag_4k|code|summarize|mixed[,...] \
  --concurrency 1,2,4,8 --requests 16 --max-tokens 128 \
  --tokenizer /path/with/tokenizer.json \
  --out results.json --md results.md
```

Options:

- `--arrival poisson:RPS` — open-loop mode: requests arrive as a Poisson process at RPS (no concurrency cap; `--concurrency` ignored, cell is labelled `poisson:RPS`). Default is closed-loop: N workers each keep one request in flight until `--requests` are done.
- `--warmup K` — untimed requests before every cell (default 1; distinct prompts from the timed set).
- `--seed` — prompt seed (default 1234). Same seed + workload + index ⇒ byte-identical request on any server.
- `--ignore-eos` — send `ignore_eos: true` (vLLM extension; plowrt accepts it) so every request emits exactly `--max-tokens` — useful for pure decode-throughput comparisons.
- `--extra-body '{"...": ...}'` — merged into every request body.
- `--dry-run` — print prompt-token distribution per workload without a server (`-v` dumps the prompts).
- `-v` — print every request as it completes.

Every request is `stream: true`, `temperature: 0`, `stream_options.include_usage: true`.
The chat template is applied server-side (we only send `messages`).

Per request (`runs[].requests[]` in the JSON): `prompt_tokens` (client tokenizer if
`--tokenizer` resolves, else server `usage.prompt_tokens`; both are also stored as
`prompt_tokens_client` / `prompt_tokens_server`), `ttft_s` (first non-empty content
delta), `tpot_s` (`(t_last_token - t_first_token) / (output_tokens - 1)`),
`latency_s`, `output_tokens` (server `usage.completion_tokens`, else count of content
chunks), `finish_reason`, `text_head` (first 80 chars), `error`.

Per (workload, concurrency) cell (`runs[].agg`): mean/p50/p90 of TTFT, TPOT, latency;
`output_tok_per_s` (sum of completion tokens / cell wall time), `req_per_s`,
`errors`. `runs[].by_kind` breaks `mixed` down by prompt kind.

### Tokenizer

`tokenizers` is not in the system Python here. The vLLM venv has it; run bench.py
with that interpreter and the pinned libstdc++ to get client-side counts:

```
LD_LIBRARY_PATH=/home/lava/vllm-cpu/gcc-lib/lib /home/lava/vllm-cpu/venv/bin/python \
  tools/bench-api/bench.py ... --tokenizer /home/lava/.claude/jobs/c77c21db/tmp/g12b-mi350-16
```

Without it, `prompt_tokens` comes from the server's `usage` (includes chat-template
tokens, so it runs ~8–15 tokens higher than the client count).

## Workloads

Prompts are composed from a bank of 12 original articles (7 paragraphs each, with
per-article questions answerable from the text), 40 stand-alone questions, 6 persona
scenarios, and 23 coding tasks (write / fix; Python, Rust, JS, Go, SQL, Bash).
Content-token ranges below were measured with the Gemma tokenizer (`--dry-run`,
40 requests, seed 1234); the server adds ~8 chat-template tokens.

| workload | content tokens (min/p50/max) | shape |
|---|---|---|
| `chat_short` | 21 / 37 / 54 | short user question, optional persona prefix + format suffix |
| `chat_long` | 230 / 382 / 668 | 2–5 consecutive article paragraphs (or a two-paragraph scenario) + question + answer instruction |
| `rag_4k` | 2359 / 3083 / 3446 | system prompt + 5–8 numbered retrieved passages (2–3 paragraphs each, from different articles, shuffled order) + question answerable from exactly one passage |
| `code` | 244 / 375 / 497 | write-a-function spec or fix-this-snippet (with code block) + optional background paragraphs + requirement bullets |
| `summarize` | 693 / 1134 / 1512 | 4–7 paragraphs of one article (optionally a "Related" section from a second) + summary instruction |
| `mixed` | 25 / 283 / 3444 | per-request random kind: chat_short 30%, chat_long 25%, code 20%, summarize 15%, rag_4k 10% |

Each request is generated by `random.Random(f"{seed}:{workload}:{index}")`, so both
servers see identical requests in the same order. For `rag_4k` the passage set and
order change per request, so prefix caching only shares the short system prompt.

## Head-to-head: plowrt vs vLLM (Gemma 4 12B, CPU)

Both servers hold the same bf16 weights (~24 GB each); this box has 58 GB, so run
them one at a time and check `free -g` (need ~38 GB available for vLLM).

### 2. vLLM

```

```

Note: `serve.sh` uses `--max-model-len 4096 --max-num-seqs 8` and
`VLLM_CPU_KVCACHE_SPACE=2` (GiB, ~8k tokens of KV). `rag_4k` at concurrency 8 is
~3.5k prompt tokens × 8 ≈ 28k tokens of KV, so vLLM will queue/preempt; raise
`VLLM_CPU_KVCACHE_SPACE` (e.g. `VLLM_CPU_KVCACHE_SPACE=8 /home/lava/vllm-cpu/serve.sh`) if
memory allows, or compare rag_4k at concurrency 1–2 only.

### 3. Compare

```
python3 tools/bench-api/compare.py plowrt.json vllm.json --labels plowrt,vllm --stat p50 --samples 2
```

Prints one markdown table (TTFT, TPOT, out tok/s, req/s per workload × concurrency,
ratio = second/first), a paired-request sanity line (prompt mismatches, identical
80-char output prefixes — greedy decoding on identical weights should agree often),
and optional sample outputs side by side.

## API notes (observed)

- Both servers honour `stream_options.include_usage`: a final chunk with empty `choices`
  and a `usage` object precedes `data: [DONE]`. vLLM additionally repeats
  `usage: null` on every chunk; plowrt omits the key until the usage chunk.
- vLLM's first SSE frame is a role-only delta (`{"role":"assistant","content":""}`)
  sent before prefill finishes; it is NOT counted as a token or as TTFT. plowrt sends
  no role frame; its `role` rides the first real token chunk.
- plowrt may emit empty-`content` chunks for partial-UTF-8 tokens (no `role` key);
  those count as tokens for TPOT but not for TTFT.
- `output_tokens` prefers `usage.completion_tokens`; the chunk count is kept as
  `content_chunks` for cross-checking.
- plowrt accepts `max_completion_tokens` as an alias for `max_tokens`, and `ignore_eos`.
- The vLLM `usage` also carries `prompt_tokens_details` and (for non-streaming)
  `prompt_logprobs`; plowrt's `usage.prompt_tokens_details.cached_tokens` reports
  prefix-cache hits.
