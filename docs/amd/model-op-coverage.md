# Model support on gfx950, by device op

What each model family needs from the device ISA, and whether the **AMD
interpreter** (`runtime/amd/interp.hip`) dispatches it. Generated by diffing
dispatched opcodes against `runtime/common/dev_isa.h`:

```sh
grep -oE "(case |in->op == )PLOW_DOP_[A-Z0-9_]*" runtime/amd/interp.hip \
  | grep -o "PLOW_DOP_[A-Z0-9_]*" | sort -u
```

Count both forms — the TP collectives dispatch via `if (in->op == ...)`, not
`case`, and a `case`-only grep undercounts them.

**AMD gfx950 dispatches 58 of 85 ISA opcodes** (was 50 before this branch: +5
fp8 prefill, +1 mxfp4, +2 MLA/gathered prefill).

Graph-level support is separate and broader: `cargo test -p rewrite --test
fuse_all_models` passes all 12 families. That tests fusion/lowering, NOT that
gfx950 can execute the result. The table below is the executable answer.

## Dense text models

| model | attention | MLP | ops | gfx950 |
|-------|-----------|-----|-----|--------|
| Gemma 3 / Gemma-31B, 12B | `FLASH_PREFILL`, `FLASH_DECODE`, `FLASH_MERGE`, `HEADNORM_ROPE` | `GEMM`/`GEMM_GLU`, `GEMV`/`GEMV_GLU`, `GEMV_QKV` | + `RMSNORM`, `NORM_RESIDUAL`, `SOFTCAP`, `ARGMAX` | **full** (prefill + decode) |
| Llama 3 | same | same | same, no softcap | **full** |
| Qwen3 | same + qk-norm | same | same | **full** |

These are the paths with fp8 coverage on both halves after this branch: fp8
decode (`GEMV_FP8`, `GEMV_GLU_FP8`), fp8 prefill (`GEMM_FP8`, `GEMM_GLU_FP8`,
`QUANT_FP8`), fp8 KV (`HEADNORM_ROPE_FP8`, `FLASH_*_FP8`), and mxfp4 decode
(`GEMV_MXFP4`).

## MLA + MoE models — Kimi K2.7, DeepSeek V2/V3, GLM 5.2

All three share the block structure (`HfArch::{Kimi, DeepSeek, Glm}` are handled
by one `synth_mla_moe` path in `crates/plowc/src/hf_config.rs`), so they share an
op set and a gap.

| component | ops | gfx950 |
|-----------|-----|--------|
| MLA decode | `FLASH_MLA_DECODE`, `MLA_MERGE_FOLD` | yes |
| MLA prefill | `FLASH_MLA_PREFILL` | yes (`PLOW_MLA_PREFILL=1`) |
| MoE routing | `MOE_ROUTER`, `MOE_ROUTER_TOPK` | yes |
| MoE experts | `MOE_EXPERT_GLU`, `MOE_EXPERT_DOWN`, `MOE_COMBINE` | yes |
| MoE block-fp8 | `MOE_EXPERT_{GLU,DOWN}_FP8_BLK`, `MOE_GROUP_{GLU,DOWN}_FP8_BLK` | yes |
| block-fp8 linears | `GEMV_FP8_BLK`, `DENSE_GLU_FP8_BLK` | yes |
| GLM DSA indexer | `INDEX_SCORE`, `INDEX_SELECT`, `FLASH_GATHER_DECODE` | yes |
| GLM DSA prefill | `FLASH_GATHER_PREFILL` | yes (`PLOW_MLA_PREFILL=1`) |
| tensor-parallel | `XREDUCE`, `XREDUCE2`, `XFLASHMERGE`, `XARGMAX_FIN` | yes |
| | `XALLGATHER`, `XREDUCESCATTER` | no |

**This gap is now closed.** `FLASH_MLA_PREFILL` and `FLASH_GATHER_PREFILL` were
defined in the ISA and absent from the AMD switch, so these three models could
decode on gfx950 but had nothing to run a real prompt through. Both now dispatch
under `PLOW_MLA_PREFILL=1`, together with the latent epilogue
(`MLA_MERGE_FOLD`, `O_UV_FOLD`) they need in the same object to finish a token.

The implementation is a generalisation, not a second kernel: `d_flash_mla_decode`
gained a query-token axis (`n_tok`), and decode is its T=1 case. MLA's absorption
already removes the per-head K/V reconstruction that makes a *dense* prefill
kernel structurally different from its decode twin, and the causal mask prefill
needs (`kv <= qpos`) was already in that loop's `keep` predicate — decode simply
never exercised it. `d_flash_mla_prefill` and `d_flash_gather_prefill` are thin
wrappers. Build cost: **zero registers** (prefill object stays 256 VGPR / occ-2).

Precondition: `nsplit` must be 1 for prefill. Under a per-token causal bound an
early token's later splits are empty, and an empty split emits `l=0` for
`d_flash_merge` to divide by. Prefill has `n_tok*n_grp` work items and does not
need the split; the opcode reuses slot `i4` (decode's `nsplit`) to carry `n_tok`.

**Still unvalidated on silicon.** Golden wrappers `mla_flash_prefill_512` and
`mla_gather_prefill_512` are in `test_kernels.hip`. The first check on hardware
day is cheap and strong: at `n_tok=1` the prefill kernel must be BIT-IDENTICAL to
the already-validated `mla_flash_decode_512` at `nsplit=1` — same kernel, T=1.

## Gemma4 MoE — not on AMD

The whole `MOE_*_GEMMA` family (router/score/topk/align, expert glu/down, group
prefill, combine, and their fp8 and w8a8 variants — 19 opcodes) is dispatched by
the NVIDIA sm120 interpreter and by nothing on AMD. `fuse_gemma4_moe` passing is
a graph-level result only.

Gemma4 **dense** is fully supported; Gemma4 **MoE** is not.

## Mamba / hybrid — not on AMD

`MAMBA2_SCAN` is NVIDIA-only and marked UNVERIFIED even there (`op_mamba.cuh`).

## Also absent on AMD (minor)

`GEMM_NORM`, `GEMV_ARGMAX`, `GEMV_SZ` / `GEMV_GLU_SZ` (split-zip compressed
weights, an NVIDIA experiment), `NOP`.

## Summary

| family | prefill | decode |
|--------|---------|--------|
| Gemma 3, Llama 3, Qwen3 (dense) | yes | yes |
| Kimi K2.7 / DeepSeek / GLM 5.2 | yes (`PLOW_MLA_PREFILL=1`, unvalidated on HW) | yes |
| Gemma4 MoE | no | no |
| Mamba2 hybrids | no | no |
