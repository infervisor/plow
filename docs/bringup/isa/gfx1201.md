## 1. The one thing to know first

Plow does **not** run native RDNA code on gfx1201 yet.

- It compiles the **CDNA (gfx942) source tree** with `-mwavefrontsize64 -mcumode`. That keeps
  every wave64 fragment, lane mask and reduction meaningful.
- The MFMA wrappers in `amd_arch.h` (`plow_mfma_bf16_32x32`, `plow_mfma_bf16_16x16`,
  `plow_mfma_fp8_32x32`) are **emulated** under `PLOW_GFX12`, using `__shfl` cross-lane permutes
  and scalar `fmaf`. The code comment says "Correct, not fast".
- **No shipped plow kernel issues a `v_wmma_*` instruction.** Only the ubench does.

So every gfx1201 prefill GEMM and attention object today runs on VALU FMAs, not the AI
accelerators.

Native work so far:

- Branch `amd-rdna4-codex-gemv` (68fc81b66, only on that branch) holds a WMMA decode GEMV
  (`runtime/amd/op_gemv_gfx12.h`). It is unmerged, unvalidated, and its microbench has never run.
  Its goals: ≥448 GB/s at M=1, Qwen3-0.6B step ≤2.8 ms [measured in plow: 68fc81b66].
- Prefill WMMA GEMM goal: ≥60% of 214.8 TF/s. No spec yet. [mixbox handoff 2026-11-03, not in repo]

[measured in plow: f5d217a48, 3a9710b74]

## 3. Matrix instructions (WMMA / SWMMAC)

There is no MFMA, no 4x4 MFMA and no `v_smfmac`. The RDNA 4 opcode list, from the
machine-readable ISA:

| Mnemonic | Shape (MxNxK) | A/B | Acc / D |
|---|---|---|---|
| `v_wmma_f32_16x16x16_f16` | 16x16x16 | f16 | f32 |
| `v_wmma_f32_16x16x16_bf16` | 16x16x16 | bf16 | f32 |
| `v_wmma_f16_16x16x16_f16` | 16x16x16 | f16 | f16 |
| `v_wmma_bf16_16x16x16_bf16` | 16x16x16 | bf16 | bf16 |
| `v_wmma_f32_16x16x16_{fp8_fp8,fp8_bf8,bf8_fp8,bf8_bf8}` | 16x16x16 | fp8 (e4m3) / bf8 (e5m2), mixed allowed | f32 |
| `v_wmma_i32_16x16x16_iu8` | 16x16x16 | int8, signed/unsigned per operand | i32 |
| `v_wmma_i32_16x16x32_iu4` (`16x16x16_iu4` also exists, same 8 cycles, half the work) | 16x16x32 | int4 | i32 |
| `v_swmmac_f32_16x16x32_{f16,bf16}`, `v_swmmac_{f16,bf16}_16x16x32_*` | 16x16x32, 2:4-sparse A | f16/bf16 | f32 or same type |
| `v_swmmac_f32_16x16x32_{fp8,bf8}_{fp8,bf8}` | 16x16x32 sparse | fp8/bf8 | f32 |
| `v_swmmac_i32_16x16x32_iu8`, `_16x16x32_iu4`, `_16x16x64_iu4` | sparse | int8 / int4 | i32 |

[vendor documented: AMD machine-readable ISA RDNA 4, instruction list and descriptions]

There is no fp4/fp6, no MX block scale, and no `f8f6f4` form. `IsaCaps.block_scale_mma` and
`mx_scale_cvt` are false.

**FP8 format is OCP.**

- The R9700 page lists FP8 as "E5M2, E4M3".
- `FeatureOCPFP8ConversionInsts` is in `FeatureISAVersion12`.
- `v_cvt_pk_fp8_f32` and `v_cvt_pk_f32_fp8` decode and encode OCP e4m3 natively. This is the
  gfx950 behaviour, not CDNA3's FNUZ.
- Plow relies on this: `PLOW_FP8_MMA_FIX` is 1.0 on gfx12, `quant_fp8` uses the hardware
  encoder, and `PLOW_GM_FP8_PACK2` takes the native path.

[vendor documented: GCNFeatures.td; AMD product page] [measured in plow: f5d217a48]

### Builtins (clang)

Pattern: `__builtin_amdgcn_wmma_<D>_16x16x16_<AB>_w32_gfx12` and `..._w64_gfx12`.
The sparse forms are `__builtin_amdgcn_swmmac_*_w32` / `_w64`. Target-feature names vary by LLVM
version (clang 21 asks for `gfx12-insts,wavefrontsize32` on a `_w32` builtin); trust the compiler
error, not a feature name.

| Builtin (`_w32` form) | w32 A, B per lane | w32 C/D | w64 A, B | w64 C/D |
|---|---|---|---|---|
| `wmma_f32_16x16x16_{f16,bf16}_w32_gfx12` | 8 x 16-bit | 8 x f32 | 4 x 16-bit | 4 x f32 |
| `wmma_f32_16x16x16_fp8_fp8_w32_gfx12` (and bf8 mixes) | `int2` | 8 x f32 | `int` | 4 x f32 |
| `wmma_i32_16x16x16_iu8_w32_gfx12(sgnA, A, sgnB, B, C, clamp)` | `int2` | 8 x i32 | `int` | 4 x i32 |
| `wmma_i32_16x16x32_iu4_w32_gfx12` | `int2` | 8 x i32 | `int` | 4 x i32 |
| `swmmac_f32_16x16x32_bf16_w32(A, B, C, idx)` | A 8 (compressed), B 16 bf16, `int` idx | 8 x f32 | A 4, B 8, `int` idx | 4 x f32 |

Upstream clang declares the bf16 operands as `short` vectors. Plow's ubench passes `__bf16`
vectors, and that compiles on the flake's ROCm 7.14.1 clang-23.

[vendor documented: clang BuiltinsAMDGPU.td] [measured in plow: runtime/ubench/wmma_rate_gfx1201.hip]

### Operand layout (16x16x16)

Let `l` = lane, `r = l % 16`, `g = l / 16` (wave32), `q = l / 16` (wave64, 0..3).

**Wave32**
- **16-bit A (f16/bf16):** lane `l` holds row `r`. Per-lane element `e` (0..7) is
  K = `4g + (e % 4) + 8*(e / 4)`. So `g=0` holds K 0-3 and 8-11; `g=1` holds K 4-7 and 12-15.
- **16-bit B:** the same, with column `r` in place of row.
- **8-bit A/B (fp8/bf8/iu8):** lane `l` holds row/column `r` and **contiguous** K `8g .. 8g+7`,
  in 2 VGPRs.
- **32-bit C/D:** lane `l` holds column `r`, rows `8g .. 8g+7` (8 VGPRs).

**Wave64**
- **16-bit A/B:** lane `l` holds row/column `r` and K `4q .. 4q+3` (2 VGPRs).
- **8-bit A/B:** lane `l` holds K `8*(q%2) + 4*(q/2) .. +3` (1 VGPR).
- **32-bit C/D:** lane `l` holds column `r`, rows `8*(q%2) + 4*(q/2) + j`, `j = 0..3` (4 VGPRs).

Sources:
- [vendor documented: RDNA 4 ISA §7.12.2 "Matrix Element Storage in VGPRs" table; AMD
  amd_matrix_instruction_calculator `matrix_calculator.py` gfx12 `_coord_to_lane_eqn` /
  `_coord_to_input_reg_eqn`].
- **Source conflict, (UNVERIFIED) until a one-WMMA oracle runs on the R9700:** the GPUOpen
  RDNA 4 example code reads as contiguous K `8g .. 8g+7` for 16-bit A/B. The ISA and the AMD
  calculator agree with each other on the split 0-3/8-11 layout above; prefer them.

What changed from gfx11 (RDNA 3):

- No duplicated A/B halves.
- No even/odd row split of C/D across lane halves.
- D therefore feeds the next WMMA's C with no shuffle.
- The layout is **not** binary-compatible with gfx11. Do not reuse `_w32` gfx11 builtins or
  fragment maps.

[vendor documented: GPUOpen "Using matrix cores of AMD RDNA 4"; RDNA 4 ISA §7.12.2]

**Porting note.**
- The emulated `plow_mfma_bf16_16x16` is the CDNA4 16x16x**32** wave64 fragment: lane `l` holds
  `A[l%16][8*(l/16)+i]`, i<8. Native wave64 gfx12 bf16 WMMA is 16x16x**16** with lane `l` holding
  K `4*(l/16)..+3`. One CDNA fragment = two WMMAs with K re-split.
- D: CDNA register `j` = row `4*(l/16)+j`; gfx12 wave64 = row `8*(q%2)+4*(q/2)+j`; wave32 =
  `8*(l/16)+j`. Re-index the epilogue.

[measured in plow: runtime/amd/amd_arch.h `plow_mfma_bf16_16x16` comment]

**Hazards (ISA §7.12.1).**
- A WMMA whose A, B or sparse index overlaps the previous WMMA's D needs at least 1 `v_nop` or
  an independent VALU op in between. This is required for correct results.
- Chaining D into C of the same WMMA type does not stall. A different type, or ABS/NEG on SRC2,
  stalls.

## 5. Synchronization and ordering

**Wait counters.** gfx12 splits the old `vmcnt`/`lgkmcnt` into separate counters, each with its
own wait instruction:

| Counter | Covers | Wait |
|---|---|---|
| `loadcnt` | global, scratch, flat and buffer loads; `global_inv` | `s_wait_loadcnt N` |
| `storecnt` | vector stores; `global_wb` | `s_wait_storecnt N` |
| `dscnt` | LDS, **and every FLAT instruction**. A FLAT load needs `loadcnt` and `dscnt`; a FLAT store needs `storecnt` and `dscnt` | `s_wait_dscnt N` |
| `kmcnt` | scalar memory (constant cache) and `s_sendmsg` / `s_sendmsg_rtn` | `s_wait_kmcnt 0` only (see below) |
| `samplecnt`, `bvhcnt`, `expcnt` | image sample, BVH, export **plus `ds_param_load` / `ds_direct_load`** | `s_wait_*` |
| combined | | `s_wait_loadcnt_dscnt`, `s_wait_storecnt_dscnt` |

- Completion is in order within a type, but may be out of order between types. **Exception:** SMEM
  loads return out of order, even to the same address. The only valid scalar wait is
  `s_wait_kmcnt 0`; a nonzero threshold proves nothing. [vendor documented: RDNA 4 ISA §5.7.1, §5.7.1.1, §5.7.1.3, §5.7.1.4]
- Never write legacy `s_waitcnt vmcnt()/lgkmcnt()`: LLVM 21 still assembles it for gfx1201, but
  its gfx12 meaning (RDNA 4 ISA §16.5: operand ignored, acts as `s_wait_idle`) is (UNVERIFIED) on
  hardware.
- Plow's macros: `PLOW_ASM_WAIT_VM(n)` → `s_wait_loadcnt n`; `PLOW_ASM_WAIT_LGKM0` →
  `s_wait_dscnt 0` + `s_wait_kmcnt 0`.

[vendor documented: AMDGPUUsage "Memory Model GFX12"; RDNA 4 ISA XML] [measured in plow: runtime/amd/amd_arch.h]

**Barrier.** It is split in two: `s_barrier_signal -1` then `s_barrier_wait -1`
(`PLOW_ASM_BARRIER`). The gfx9 single `s_barrier` is gone from inline asm. `__syncthreads()`
lowers correctly. [measured in plow: f5d217a48]

**Scopes.**

- LLVM `agent` maps to `scope:SCOPE_DEV`; `system` maps to `SCOPE_SYS`.
- `workgroup` maps to nothing in CU mode and to `SCOPE_SE` in WGP mode.
- `global_inv scope:X` invalidates every cache whose scope is strictly smaller than X.
- `global_wb` is needed only for `SCOPE_SYS` on gfx120x.
- An agent-scope acquire fence is: wait on `storecnt`, `loadcnt` and `dscnt`, then `global_inv`.
- A system-scope release adds `global_wb scope:SCOPE_SYS` before the waits.
- Plow's `plow_cache_inv()` (gfx9 `buffer_inv`) is `__builtin_amdgcn_fence(acquire, "agent")` on
  gfx12.
- Drain loads and atomics before a system-scope store in hand-written asm
  (`FeatureWaitsBeforeSystemScopeStores`, llvm-project main; absent in LLVM 21).

[vendor documented: AMDGPUUsage GFX12 tables; GCNFeatures.td]

**Coherence.**

- In CU mode, waves of one workgroup share the L0, so a workgroup barrier needs no L0
  invalidate. WGP mode would need `global_inv scope:SCOPE_SE`.
- The scalar L0 is not coherent with the vector L0. Never read data another wave just wrote
  through `s_load`.
- The CP invalidates caches at each dispatch. On a dGPU, kernargs are read uncached.

[vendor documented: AMDGPUUsage GFX12]

**Host-dispatch scope.** Plow dispatches with **SYSTEM** acquire/release fences on agents whose
native wave is 32 (`hsa_backend.c` `dispatch_scope`). CDNA keeps AGENT scope. With AGENT scope,
gfx1201 kernels read stale L2 lines of a host buffer the CPU had just rewritten.
[measured in plow: deda2a694]

**Clock.** `s_memrealtime` does not exist. Convert ticks with `HSA_AMD_AGENT_INFO_TIMESTAMP_FREQUENCY`
(1–400 MHz per `hsa_ext_amd.h`; 100 MHz is typical, not guaranteed). Plow reads REALTIME with
`s_sendmsg_rtn_b64` (`MSG_RTN_GET_REALTIME` 0x83, `__builtin_amdgcn_s_sendmsg_rtnl(0x83)`), in
`plow_realtime()`. [vendor documented: RDNA 4 ISA XML has `S_SENDMSG_RTN_B64`, no `S_MEMREALTIME`] [measured in plow: f5d217a48]

## 6. Toolchain as plow uses it

**Compiler.**

- `hipcc` from the flake: ROCm 7.14.1 (TheRock gfx94X build, clang-23).
- `scripts/build_gfx942.sh` asserts `PLOW_TOOLCHAIN_LABEL=rocm-7.14.1-nix` and reads

**Builtin style.** Wrap anything arch-specific in `amd_arch.h`. Op bodies never name a builtin
that only one arch has (docs/arch/14-amd-arch-divergence.md §3.1). Chapter 14 still describes
only CDNA3/CDNA4; gfx12 is a third arm of the same header.

```cpp
#if PLOW_GFX12
typedef __bf16 bf16x8w __attribute__((ext_vector_type(8)));   // wave32: 8 per lane
typedef float  f32x8w  __attribute__((ext_vector_type(8)));
acc = __builtin_amdgcn_wmma_f32_16x16x16_bf16_w32_gfx12(a, b, acc);  // needs wave32 build
asm volatile(PLOW_ASM_WAIT_VM(0) "\n\ts_wait_dscnt 0" ::: "memory");
#endif
```

`_w32_` builtins are rejected in a `-mwavefrontsize64` object. Use `_w64_gfx12` (half the VGPRs per lane)
there, or build that object wave32.

## 7. Pitfalls

1. **The inlined MFMA emulation broke the dispatch.** The permute emulation, inlined into the
   GEMM/attention bodies, pushed the prefill object to about 13 KB/lane of scratch. The dispatch
   never launched: the AQL read index stuck at that packet and looked like a hang. The fix is
   `PLOW_MMA_FN = noinline` on gfx12, which gives 1.66 KB/lane (gfx942: 1.25 KB). Keep the
   wrappers out of line until native WMMA bodies land. [measured in plow: 3a9710b74]
2. **`interp_decode_gq` scratch and spills.**
   - It uses 636 / 1424 / 1384 / 2644 / 5332 B/lane of scratch at M = 1/2/4/8/16, with 2–9 VGPR
     spills. This is open.
   - Repro: `PLOW_HIP_ARCH=gfx1201 PLOW_ROWS_ONLY='=interp_decode_gq' scripts/build_gfx942.sh <out>`
     plus `-Rpass-analysis=kernel-resource-usage`.
   - Do not add register pressure to decode bodies without re-checking this.

   [measured in plow: mixbox amd-rdna4 handoff, not in repo]
3. **A hung dispatch hangs the drain.** A wedged dispatch hung the engine thread and the SIGTERM
   drain. `PLOW_AMD_HANG_TIMEOUT_S` (default 300) now fails with the AQL read/write indices.
   Expect that message, not a silent hang, when an object over-asks for scratch.
   [measured in plow: c1769abe2]
4. **The agent reports wave32 even for wave64 objects.** `HSA_AGENT_INFO_WAVEFRONT_SIZE`
   returns 32. Plow's dispatch width is 64 lanes on every AMD arch. Do not derive the launch
   width from the agent. [measured in plow: f5d217a48, runtime/amd/hsa_backend.c]
5. **Agent-scope dispatch fences read stale host data.** RDNA agents need SYSTEM-scope AQL
   acquire/release when the host rewrites a buffer between launches.
   [measured in plow: deda2a694]
6. **The HSA pool flag values were wrong.** Before the fix, plow used the wrong flag values
   (correct: KERNARG=1, FINE=2, COARSE=4), so VRAM came from the fine pool and kernargs from
   coarse host memory. gfx1201 has only coarse VRAM. [measured in plow: f5d217a48]
7. **hwreg 20 is not XCC_ID on gfx12.** It is the scratch base. The `s_getreg` XCD read in
   `interp.hip` is compiled out under `PLOW_GFX12`. The L2-hierarchy gates (`PLOW_GATE_HIER*`,
   `PLOW_L2_PLACE_DISPATCH`) do not apply, because there is one L2 domain.
   [measured in plow: cba10b981]
8. **gfx9 store scopes `#error`.** `PLOW_GATE_SC1` emits gfx9 `sc0 sc1` stores and refuses on
   gfx12. Use `scope:` / `th:` or the builtin `aux` encoding (`PLOW_BUF_AUX_NT`).
   [measured in plow: runtime/amd/amd_common.h]
9. **Buffer resource word 3 fails silently.** The gfx9 constant returns zeros for every lane
   with no fault. [measured in plow: f5d217a48]
10. **No LDS DMA.** `__builtin_amdgcn_global_load_lds` does not compile for gfx1201 (needs
    `vmem-to-lds-load-insts`). Use plow's VGPR-staged `cp_async4` and drain `dscnt` as well as
    `loadcnt` before the barrier. [measured in plow: cba10b981] [vendor documented: GCNFeatures.td]
11. **`_k3` decode rows overflow LDS by 8 B.** At decode batch 1 `interp_decode_k3` and
    `interp_decode_fp8kv_k3` overflow the 64 KiB arena (gfx942 too; not gfx950's 160 KiB).
    gfx1201 config builds drop `_k3` rows when the packet has no K3 opcode.
    [measured in plow: scripts/build_gfx942.sh "A gfx1201 config build drops"; c1bda65c6]
12. **12B BF16 at batch 8 does not load on one 32 GB card.**
    - The flat slab asks for a single allocation of about 47 GB.
    - The per-tensor fallback then gets `HSA_STATUS_ERROR_OUT_OF_RESOURCES`.
    - Size the KV and batch for 32 GB, not for MI300X. This is open.

    [measured in plow: mixbox amd-rdna4 handoff, not in repo]
13. **Set `iommu=pt` before any peer test.** Without it peer stores were dropped silently while
    `memcpyPeer` reported 110 GB/s (NVIDIA pair, same host). With it R9700↔R9700 peer atomics are
    correct (fine 2.74 µs, coarse 2.96 µs RTT). Cross-vendor peer is not assumed; use the staged
    host path (docs/arch/30). [mixbox handoff, not in repo]
14. **`IsaCaps.warp_lanes = 64` describes plow's build, not the hardware.** A native-wave32
    kernel must not read wave width from hwspec. [measured in plow: crates/hwspec/src/isa.rs comment]
15. **Batched-rung numerics differ from rung 1.** Seeded concurrent and solo text differ, as on
    NVIDIA (not batch-invariant). The 12B BF16 b1 FP32 gate has an unexplained KL tail: 19
    over-limit positions, kl_p99 0.37, with no same-checkpoint peer yet.
    [mixbox handoff, not in repo]
16. **The gfx11 WMMA layout is incompatible.** gfx11 builtins and fragment maps are wrong on
    gfx12. [vendor documented: GPUOpen RDNA 4 matrix cores]

## 9. Decision checklist

- **Writing a GEMM/attention body for gfx1201:** write a native `PLOW_GFX12` arm with
  `v_wmma_*_16x16x16`. Do not tune the emulated `plow_mfma_*` path; it is VALU-bound by
  construction. Keep the arm a separate function next to the CDNA one (docs/arch/14 §4 fork rule).
- **Choosing wave size for a new native kernel:**
  - Wave32 gives the full WMMA fragment (8 per lane), VOPD, and 1536 VGPRs per SIMD.
  - Wave64 keeps the shared CDNA fragment code but uses `_w64_gfx12` (half the VGPRs per lane).
  - Wave size is per kernel (`.amdhsa_wavefront_size32`); plow's build rows pick one per row,
    so a different wave size takes a separate row in `build_gfx942.sh`.
- **Picking a tile:** stay within 64 KiB of LDS per workgroup. The 128 KiB per WGP is reachable
  only as two workgroups. Size the CU-mode occupancy against 16 waves/SIMD and the 24/12 VGPR
  granule, not CDNA's 512-VGPR or AGPR budget.
- **Staging global→LDS:** there is no LDS DMA. Use `global_load_b128` into VGPRs, then
  `ds_store_b128`, double-buffered in registers. Wait on `s_wait_loadcnt` before the store and
  `s_wait_dscnt` before the barrier. For transposed bf16/fp8 B operands, try
  `global_load_tr_b128` / `_tr_b64` before an LDS transpose.
- **Writing decode GEMV:** it is bandwidth bound at 640 GB/s. Use `buffer_load_b128` with the
  gfx12 resource word and `PLOW_BUF_AUX_NT`. Replace the widen+2xFMA dot with `v_dot2_f32_bf16`
  (or WMMA for M at least 2). Check the result against `interp_decode_gq`'s existing spills.
- **Hand-writing waits or barriers:** use `PLOW_ASM_WAIT_VM`, `PLOW_ASM_WAIT_LGKM0` and
  `PLOW_ASM_BARRIER`, never a literal `s_waitcnt` or `s_barrier`.
- **Publishing data to another workgroup:** bump the flag with a release atomic at agent scope;
  the consumer does an acquire (relaxed load + `plow_cache_inv()`) before reading the payload, as
  `interp.hip` `ctr_acquire` / release `__hip_atomic_fetch_add`. A fence alone does not
  synchronize. For host output, rely on the SYSTEM-scope dispatch fence. Never `buffer_inv` or `sc0/sc1`.
- **Handling fp8:** bytes are OCP e4m3 natively. Do not port CDNA3's FNUZ halving, the
  `0x80` mask, or `PLOW_FP8_MMA_FIX = 4`.
- **Adding a gfx12-only interpreter arm:** gate it `#if PLOW_GFX12` with its marker symbol, as
  for `GEMV_ARGMAX` and the other gfx12 arms in `interp.hip`. Prove CDNA unchanged: gfx942
  per-kernel disassembly diff, gfx950 preprocessed-source diff (c1bda65c6 method).
- **Before any GPU measurement:** build the probe and the object under `nix develop`, then submit
  with `gpuq.py --vendor amd`. Check scratch and spills from the ISA (`plow_isa.py`), not just
  `.vgpr_spill_count`. Large scratch can block a dispatch outright.
- **Quoting %-of-roofline:** say "datasheet 640 / 191 / 383"; 639.9 GB/s and 214.8 / 400 TF/s
  are unarchived handoff numbers (§8), so label them so.
- **Planning multi-GPU on R9700:** PCIe 5 only, no XGMI. Same-vendor peer works with
  `iommu=pt`; cross-vendor goes through the staged host path at about 50 GB/s per hop.
