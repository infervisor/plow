## 2. Matrix instructions (MFMA, XDL)

All new shapes need `gfx950-insts` (clang: "needs target feature gfx950-insts" on gfx942,
`runtime/amd/amd_arch.h` header). Pass counts are LLVM's `SIDPGFX950FullSpeedModel`; one pass =
4 cycles [vendor documented: CDNA4 ISA §7.6]. Cycle counts per CDNA4 ISA Table 28 / §7.1.5:
32x32x16 bf16/f16 32, 16x16x32 bf16/f16 16, 32x32x16 fp8_fp8 32 (= the bf16 cost),
32x32x64 f8f6f4 64 if either operand is f8 else 32, 16x16x128 f8f6f4 32 / 16.

- Per-CU datasheet rates check out: MI355X bf16 2.5 PF / (256 CU x 2.4 GHz) = 4096 FLOP/clk/CU;
  fp8 x2, MXFP6/MXFP4 x4. bf16/fp16 doubled vs gfx942; FP64 matrix halved (ROCm MI350 perf table:
  78.6 TF MI355X). No xf32 MFMA on gfx950: `FeatureXF32Insts` is in the gfx942 set and absent from
  `FeatureISAVersion9_5_Common` [vendor documented: LLVM GCNFeatures.td].
- hwspec `CDNA4_CU.mma` = 512 bf16 / 1024 fp8 / 2048 fp4 / 1024 int8 MAC/clk per matrix core
  (4 per CU) = the same numbers.
- Fragment maps. 32x32xK: lane `l` holds row `l%32`, k-slots `8*(l/32)+[0..7]` per 16 k
  (bf16; 16x16x32: lane group `l/16` holds k `8*(l/16)+[0..7]`) [vendor documented: CDNA4 ISA
  §7.1.5.1 BF16 layouts]. For fp4 (cbsz/blgp=4) K=64, lane `l` holds row `l%32`, k = `32*(l/32)+[0..31]`; the
  per-32-k E8M0 scales would expose a wrong grouping, so this map is pinned by measurement
  [measured in plow: runtime/amd/amd_common.h A4W4 block, runtime/tests/a4w4_gfx950_test.hip].
  The fp4 map is also the vendor map (CDNA4 ISA §7.1.5.1: `A[i,k]` in item `k%32` of lane
  `i + 32*(k/32)`). For **fp8** K=64 the vendor map differs: lanes 0-31 hold k 0-15 (v0-3) and
  k 32-47 (v4-7), lanes 32-63 hold k 16-31 and 48-63; fp6 is contiguous like fp4 (lanes 0-31 k 0-31, lanes 32-63 k 32-63,
  six dwords) [vendor documented: CDNA4 ISA §7.1.5.1 FP8/FP6 diagrams]. plow's `d_gemm_fp8_t` loads the fp4-style contiguous map (op_gemm_common.h FP8 section) and
  is still correct because A and B are permuted identically with neutral scales; do not reuse that
  map where per-32-k scales or a k-dependent epilogue make the permutation visible.
  Accumulator layout of every 32x32 form equals the bf16 one (`mfma_acc_m/mfma_acc_n`, amd_common.h).
  16x16x128 (CDNA4 ISA §7.1.5.1): row/col = `l%16`; fp4 lane group `l/16` holds k
  `32*(l/16)+[0..31]`; fp8 lane group g holds k `16g+[0..15]` (v0-3) and `64+16g+[0..15]` (v4-7).
  One E8M0 scale per 32 K per row; op_sel picks the scale byte (plow: `moe_down_a4w4_sweep.h`).
- Scale semantics: ABID[0]=1 is required for the `V_MFMA_SCALE_*` forms; ABID[0]=0 forces both
  scales to 1.0 (0x7f) — the unscaled encoding. Result exponent adds `scale_a + scale_b`
  [vendor documented: CDNA4 ISA §7.1.5 rules table]. Src0/1/2/vdst VGPRs must be even-aligned;
  EXEC is ignored (forced all-ones); round mode forced RNE.
- One gfx950 bf16 issue == two gfx942 issues over the two halves of the same lane fragment; the
  fragment map is identical, which is what makes cross-arch GEMM comparisons bit-meaningful
  (arch/14 §3.1).

### Scaled MFMA (MX block scales)

- Builtin arg order (9): `(a, b, acc, cbsz, blgp, opsel_a, scale_a, opsel_b, scale_b)`.
  `cbsz`/`blgp` (compile-time) select A/B format: 0 = fp8 e4m3, 1 = bf8 e5m2, 2 = fp6 e2m3,
  3 = bf6 e3m2, 4 = fp4 e2m1 [vendor documented: LLVM SIDefines.h `MFMAScaleFormats`]. The builtin
  takes v8i32 operands for every format (clang rejects v4i32); hardware reads 8/6/4 dwords for
  f8/f6/f4, so zero-fill the unread upper dwords.
- `opsel_*` is a 2-bit byte select into the 32-bit scale register; `scale_*` is a runtime i32
  holding E8M0 bytes, one per 32 K-elements per row [vendor documented: IntrinsicsAMDGPU.td
  `AMDGPUMfmaScaleIntrinsic`]. Encodes as a `v_mfma_ld_scale_b32` + MFMA pair (VOP3PX).
- E8M0 byte `b` (0-254) = 2^(b-127); 0xFF is NaN [vendor documented: CDNA4 ISA §7.2]. Neutral is **127**; byte 0 is 2^-127, not 0: both scales 0 → 2^-254 (underflows), one side 0 → 2^-127·a·b (can stay normal).
- Scale args that are the **constant 0** (both A and B) make the backend emit the UNSCALED
  `v_mfma_f32_32x32x64_f8f6f4` / `16x16x128_f8f6f4` and drop the scales
  [vendor documented: LLVM SIInstrInfo.td `UnscaledMFMAOptimizationPat`, matches `0` only]. Any
  other value, constant or runtime, keeps `v_mfma_scale_*`, where byte 0 means 2^-127. There is no
  dense unscaled builtin, so "scaled builtin with constant-0 scales" is how plow gets dense fp8 K=64.

| mechanism | gfx950 | notes |
|---|---|---|
| `global_load_lds_{u,s}byte`, `_{u,s}short`, `_dword`, `_dwordx3`, `_dwordx4`; `buffer_load_dword{,x3,x4} … lds` | `__builtin_amdgcn_global_load_lds(src, lds, size, off, aux)`, size in **bytes** 1/2/4/**12/16** | 12/16 are gfx950-only [vendor documented: clang SemaAMDGPU.cpp; LLVM FLATInstructions.td `GLOBAL_LOAD_LDS_DWORDX3/X4`]. plow: `cp_async16` (amd_common.h) |
| LDS destination | from **M0, wave-uniform**; lane `l` lands at `M0 + 4*l` for 1/2/4-byte sizes and `M0 + 16*l` for 12/16-byte sizes (dwordx3 writes 12 B and skips the 4th dword) [vendor documented: CDNA4 ISA §9.1.9; LLVM AMDGPUDMAOperations.md] | per-lane LDS addresses are silently ignored (`v_readfirstlane`) [measured in plow: amd_common.h ASYNC HBM->LDS] |
| `ds_read_b64_tr_b{4,8,16}`, `ds_read_b96_tr_b6` | `__builtin_amdgcn_ds_read_tr{4,8,16}_b64_*`, `…_tr6_b96_v3i32` | transpose loads, gfx950-only [vendor documented: LLVM DSInstructions.td, BuiltinsAMDGPU.td]. plow: `mla_pf_ds_read_tr16` (`__builtin_amdgcn_ds_read_tr16_b64_v4bf16`) in `op_attention_gfx950.h`, used by `mla_mha_pf.h`, `mla_sparse_pf.h`, `op_attention_common.h`; `mla_pf_dense_gfx950.hip` has its own `mla_pfd_tr16` |
| f8f6f4 operand fragments | normal DS reads | fp8 K=64 fragment = 32 B/lane (two `ds_read_b128`); fp4 = 16 B/lane (one `ds_read_b128`) (amd_common.h A4W4 block) |
| buffer loads | `__builtin_amdgcn_make_buffer_rsrc` + raw buffer loads (`buf_rsrc_fp8`, `buffer_load_dwordx4 … offen`) | same as gfx942 |
| non-temporal stores | `__builtin_nontemporal_store` 128 B lines | `MOE_DOWN_SWEEP_LINE` 8k 0.73->0.48 ms [measured in plow: docs/amd/glm53-mxfp4-mi350x.md] |

tr16 semantics as plow relies on them: one `ds_read_b64_tr_b16` returns 4 bf16 = one column
slice of 4 consecutive LDS rows, laid out per 16-lane group as 4 rows x 16 columns; two of them
form the bf16x8 B fragment of a 32x32x16 PV MFMA in the S^T accumulator's own k permutation
{4g..4g+3, 4g+8..4g+11} [measured in plow: runtime/amd/mla_mha_pf.h header; commit 42597ee7].
Vendor rules [vendor documented: CDNA4 ISA §11.4]: EXEC must be all ones; the LDS address must be
aligned to the data size (8 B for b64); destination VGPR pair even-aligned (`b96_tr_b6` excepted);
a full fragment takes two instructions — for b16 the first loads K=0..3 and 8..11, the second
K=4..7 and 12..15, each lane holding 4 consecutive M/N values; b8: K 0-7,16-23,32-39,48-55 then
the rest; b4: K 0-15, 32-47 then the rest.

Bank-conflict rules (64 banks x 4 B):

- Check row strides mod 64 dwords, not 32. plow's MLA row-pair stride 1120 B = 280 dwords ≡ 24
  (mod 64) is conflict-free for the 16-lane b128 K pass and the 4-row x 8-dword tr16 group (`mla_mha_pf.h`).
- GEMM tiles: `+8` halves (16 B) row padding (`GemmTile::PAD_HALVES`); fp8 tiles use a 32-byte XOR
  swizzle (`GM8_XORSWZ`, op_gemm_common.h fp8 section).
- `global_load_lds` lays lanes down at a fixed lane stride (4 B for <=4-byte sizes, 16 B for 12/16;
  [vendor documented: LLVM docs/AMDGPUDMAOperations.md]), so a padded LDS tile must be
  filled in runs that never cross the pad (amd_common.h `cp_async4` note).
- LDS base alignment matters: a 4-byte-aligned arena silently split `ds_read_b128` into
  `ds_read2_b32` pairs (see pitfalls).

## 4. Synchronization and ordering

Same model as gfx942 (see gfx942.md); LLVM documents it in "Memory Model GFX942", and gfx950's
feature set is the 9.4 common set plus additions (`FeatureISAVersion9_5_Common`), so the same code
sequences apply [vendor documented: AMDGPUUsage.md "Memory Model GFX942"; GCNFeatures.td].

- `s_waitcnt vmcnt(N)` covers global/buffer loads **including `global_load_lds`**. In-flight DMA
  continues across `s_barrier`: issue before a gate; before any other wave reads the tile, every
  issuing wave runs `cp_async_wait()` (`vmcnt(0)`), then `__syncthreads()` (`op_gemm_common.h` DIRECT path).
- Wait counters cover only the issuing wave: `lgkmcnt(0)` then a barrier publishes LDS writes.
- `buffer_inv` SC bits [vendor documented: CDNA4 ISA §9.1.10 Table 52]: `sc1=0 sc0=0` = NOP for
  both CU cache and L2; `sc0` alone = invalidate the CU cache **only in TG-split mode**, NOP
  otherwise; `sc1` = invalidate the CU cache + (with >1 L2) non-coherently cached L2 lines;
  `sc1 sc0` = CU cache + L2. So outside TG-split there is **no L1-only invalidate**: the cheapest
  instruction that drops this CU's stale L1 lines is `buffer_inv sc1`. `buffer_wbl2` (Table 51):
  `sc1=0` = NOP; `sc1=1` writes back dirty L2 (when >1 L2). AMDGPUUsage "Memory Model GFX942" and
  SIMemoryLegalizer.cpp agree.
- Agent-scope acquire = acquiring load, `s_waitcnt vmcnt(0)`, `buffer_inv sc1` (CU L1 + L2); agent
  release = `buffer_wbl2 sc1` + `s_waitcnt vmcnt(0)`. Workgroup scope emits neither.
- The L2 part of `buffer_inv sc1` and `buffer_wbl2` is per-L2: 256 workgroups issuing them makes
  each XCD's L2 do the same work 32 times, serialised. The L1 part is per CU, so one leader per XCD
  cannot replace every CU's own L1 invalidate. plow's gfx950 decode GQ objects default `PLOW_GATE_HIER=1`:
  one leader per XCD does the L2 maintenance with XCD-local rendezvous, and followers are meant to
  invalidate only their own L1 (runtime/amd/interp.hip, `runtime/CMakeLists.txt` `PLOW_GATE_HIER`)
  — but see pitfall 23: the follower instruction is a bare `buffer_inv`, which Table 52 makes a NOP.
- MFMA hazards are scheduled by the compiler for builtins; hand asm must insert wait states per
  CDNA4 ISA §7.6 Table 38 (by producer passes 2 / 4 / 8 / 16). Non-DL VALU write -> MFMA read: 2.
  XDL write -> XDL SrcC exactly the same vDst, same passes: 2 / 0 / 0 / 0; overlapping otherwise:
  4 / 6 / 10 / 18. XDL write -> SrcA/B read, or VM/LDS/FLAT/VALU access of the result: 5 / 8 / 12 / 20.
- `__builtin_amdgcn_s_setprio(1/0)` around MFMA bursts, `sched_group_barrier`/`sched_barrier` to
  pin interleave; `s_barrier` clusters implement the ping-pong in `d_gemm_t` (op_gemm_common.h).

## 6. Pitfalls

1. Scaled MFMA whose two scale args are the **constant 0** lowers to the unscaled
   `v_mfma_f32_32x32x64_f8f6f4` and drops the scales; any other scale (runtime, or a non-zero
   constant) selects `v_mfma_scale_*`, where byte 0 = 2^-127, not 1.0 (neutral = 127).
   `d_gemm_fp8_t`'s comment "byte 0 = neutral" is right about that kernel only because its zeros
   are constant. Assert the scaled mnemonic for any MX kernel.
   [measured in plow: runtime/amd/amd_common.h A4W4 block; runtime/tests/a4w4_gfx950_test.hip;
   vendor documented: LLVM SIInstrInfo.td `UnscaledMFMAOptimizationPat`]
2. `v_mfma_f32_32x32x16_fp8_fp8` runs at the bf16 rate (2265 TF/s pure issue, same as
   `32x32x16_bf16`); the 2x fp8 rate comes only from the K=64 f8f6f4 family — the unscaled
   `v_mfma_f32_32x32x64_f8f6f4` (what `plow_mfma_fp8_32x32` emits and the asm contract requires)
   or `v_mfma_scale_*`, same 16-pass cost (4532 TF/s pure issue). The asm contract forbids the K16 fp8 forms on gfx950; gfx942 requires them in fp8 objects only.
   [measured in plow: runtime/amd/op_gemm_common.h FP8 section; scripts/asm_expect_gfx950.json]
3. A4W4 can silently degrade to w4a16: an fp4 operand widened to bf16 because a convert did not
   fold is numerically correct at <= 1/4 of the fp4 MFMA rate (bf16 512 vs fp4 2048 MAC/clk, `mi350.rs`). Only the disassembly sees it.
   [measured in plow: scripts/asm_expect_gfx950.json `_a4w4_note`]
4. Native fp8 K64 GEMM reached only bf16 parity (q 594 vs 603 TF/s; MfmaUtil 30% -> 15%) and
   3-4x short of hipBLASLt fp8 (~2600 TF/s): the wall is the LDS-read -> MFMA dependency chain,
   not barrier count or memory. Wider K per issue does not help without deep register prefetch.
   [measured in plow: runtime/amd/op_gemm_common.h "FP8 (w8a8) PREFILL GEMM"]
5. Dense MFMA on all 256 CUs pulls the clock to ~1.58 GHz (power-limited, junction 57 C): sustained
   bf16 ceiling 1660 TF/s, not 2300. Single-CU numbers extrapolate to a fake 2308.
   [measured in plow: runtime/amd/op_gemm_common.h MEASURED CEILINGS]
6. Best tile is K- and power-dependent: through the interpreter 192x256 beats 256x256 at K=2560
   (Qwen3-4B, o +32%) while 256x256 wins at K=5376 (Gemma-31B); standalone runs invert this. Always
   interleave arms; a cold clock ramp manufactures fake winners.
   [measured in plow: runtime/amd/op_gemm_common.h TILE / NON-POWER-OF-2 TILES]
7. HBM saturates on loads in flight, not wave count: 4 waves x unroll-4 = 5908 GB/s,
   16 waves x unroll-1 = 6173 GB/s; plan for >=4 outstanding 16 B loads per lane.
   [measured in plow: runtime/amd/op_gemm_common.h]
8. `global_load_lds` LDS destination is M0 (wave-uniform); per-lane LDS pointers are ignored.
   CDNA3's 4 B issues cannot emulate the 16 B layout. clang-23 retyped the builtin's global
   operand to non-const `void*`: pre-23 spelling stops compiling on every arch (version-gated in
   `cp_async16`). [measured in plow: runtime/amd/amd_common.h ASYNC HBM -> LDS]
9. `__builtin_amdgcn_global_load_lds` used in a `__device__` body without `__HIP_DEVICE_COMPILE__`
   fails the host pass with "invalid size value" — a misleading message.
   [measured in plow: runtime/amd/amd_common.h]
10. A 4-byte-aligned LDS arena degraded every `ds_read_b128` to `ds_read2_b32` pairs, which made
    8 waves look 2.2x better than 4; after the alignment fix the real gain is +7%.
    [measured in plow: runtime/amd/op_gemm_common.h WAVE COUNT]
11. Producer/consumer wave specialisation wastes registers: AMD partitions the VGPR file
    statically across all waves of the workgroup, so a producer wave burns its allocation. Use
    the ping-pong (one extra `s_barrier` for group 1) instead. [measured in plow: op_gemm_common.h]
12. `v_cvt_scalef32_pk_bf16_fp8`'s scale is E8M0-only (only the f32 exponent survives): folding a
    DeepSeek/GLM f32 `weight_scale_inv` of 0.01 lands 22% low. Use it with scale 1.0 and multiply
    each 128-K block partial by its f32 scale before summing (`gemv_rows_fp8_blk`). Its `word_sel` picks an adjacent byte pair (false = bytes 0-1,
    true = bytes 2-3, same order as `cvt_pk_f32_fp8`); the older "broadcasts one byte" note at
    amd_common.h ~L469 is retracted by the comment at ~L630-653.
    [measured in plow: runtime/amd/amd_common.h ~L469, ~L681; hwspec `mx_scale_cvt` doc]
13. Register cliff: 8-wave objects over 256 VGPR+AGPR drop to 1 wave/SIMD and past budget fail at
    load with `HSA_STATUS_ERROR_INVALID_ISA`. fp8/MLA prefill objects were 262/occ-1 under ROCm
    7.0.2/clang-20 and 256/occ-2 under 7.2.4/clang-22 — a toolchain bump moves it.
    [measured in plow: runtime/cmake/hipcc_hsaco.sh]
14. Agent-scope acquire inside a spin loop issues `buffer_inv` every poll (~2x decode cost). Poll
    relaxed, one acquire after. Narrowing to workgroup scope is a real race (100% stale reads,
    cross- and same-XCD, because L1 is per CU). [measured in plow: runtime/amd/interp.hip ctr_poll note]
15. Cache maintenance, not the atomic, dominates an empty 256-WG gate (13.16 us baseline; per-XCD
    leader 3.46 us); gate stall was 21% of a Gemma-4 31B decode token on MI355X [measured in plow:
    `interp.hip` gate-sentinel comment]. `PLOW_GATE_HIER` on: K3 TP8 decode TPOT -17.1% [measured in plow: 90344c6b].
16. Host pass of a hipcc executable build has `PLOW_CDNA4 == 0` and parses the gfx942 arm; a
    kernelcaps probe that took the last resource line reported host-pass CDNA3 tiles for gfx950.
    [measured in plow: crates/kernelcaps/src/probe.rs L565]
17. A host-side duplicate of the LDS budget (`GM_LDS_HALVES` 73,728 = the CDNA4 value) let the
    emitter fuse batches that overflowed gfx942 objects — every batched-decode blob on gfx942 was
    wrong. The gfx950 value is the large one; never let it leak into a shared constant.
    [measured in plow: docs/arch/14-amd-arch-divergence.md §5]
18. Knobs measured on gfx942 (`FA_FAST_RCP`, `FA_MERGE_UNROLL4`, `FA_MLA_PF2_DEFER`, `GV_USCALAR`,
    `GV_RS_WIDE`, `PLOW_GV_UN_FP8_KDIV`) stay OFF on gfx950 until its goldens are re-run; object
    growth alone once regressed gfx950 decode 32%. [measured in plow: op_gemm_gfx950.h,
    op_attention_gfx950.h]
19. FP8 block GEMM DMA on 64x128 tiles mismatched (cause not found); kept on BM=128 only. MoE
    stage-1 wide tile (A+B via LDS) bit-exact but slower (423 -> 501 us). XR sched 24/8 (gfx942
    default) no gain on gfx950. [measured in plow: docs/amd/glm53-mxfp4-mi350x.md "Negatives"]
20. tr16 PV loads: -16.6% isolated MLA-prefill body, bit-exact, no occupancy change
    (256 scalar `ds_read_u16` + 128 `v_perm_b32` -> 64 transpose reads). gfx942 has no such
    instruction; sources `#error` there. [measured in plow: commit 42597ee7]
21. The W8A8 scheme (per-row activation x per-channel weight) runs scaled MFMA with neutral MX
    scales and applies scales in the epilogue; the MX per-32 scale is not plow's dense fp8 scheme.
    `moe_pf_w8a8.h` deliberately rides a 2^-4 lo-term on the A scale byte (123).
    [measured in plow: runtime/amd/op_gemm_common.h, runtime/amd/moe_pf_w8a8.h]
22. LDS is 64 banks on gfx950 vs 32 on gfx942: strides tuned "mod 32" on gfx942 can conflict here
    and vice versa. [vendor documented: LLVM GCNFeatures.td `FeatureLDSBankCount64`]
23. **Bare `buffer_inv` is a NOP**, and `sc0` alone is a NOP outside TG-split [vendor documented:
    CDNA4 ISA Table 52]. The `PLOW_GATE_HIER` followers' `ctr_acquire_l1()` (`interp.hip`) is a bare
    `buffer_inv` its comment calls "L1 only", so it invalidates nothing: **suspected race, needs a
    resident-line stress test on gfx950**; fix = followers issue `buffer_inv sc1`. Other bare sites
    (`interp.hip` ~L3424-3523, 4621, 4687, 6049; `hc_mix_decode.hip:192`; `router_decode.hip:58`;
    `op_gemm_common.h:1382`) are redundant where an agent-acquire RMW precedes them; check each.
    Never write a bare `buffer_inv`.

## 8. Decision checklist

- Writing a bf16 GEMM/attention inner loop: use `plow_mfma_bf16_32x32` / `_16x16` from
  `amd_arch.h`, never a raw builtin in an op body (arch/14 §3.1).
- fp8 GEMM: use `v_mfma_scale_f32_32x32x64_f8f6f4` (cbsz=blgp=0); add an `asm_expect_gfx950.json`
  rule forbidding `*_fp8_fp8`. Expect parity with bf16 unless you also break the LDS->MFMA chain
  with deep register prefetch; for big prefill GEMMs compare against the hipBLASLt route first.
- MXFP4/MXFP6 x MX activations: scaled MFMA with real E8M0 scales (127 = 1.0; never constant 0), operand
  v8i32 with upper dwords zero for fp4; add a `fmt_on` rule (cbsz/blgp per mnemonic) for
  `v_mfma_scale_*` in `asm_expect_gfx950.json`.
- MXFP4 weight-only decode: `v_cvt_scalef32_pk_bf16_fp4` + `v_dot2c_f32_bf16`, no MFMA (contract
  `interp_decode_mxfp4`).
- Non-power-of-two (f32) block scales: do not fold into `cvt_scalef32`; scale each K-block partial.
- Staging to LDS: `cp_async16` (16 B/lane `global_load_lds_dwordx4`) with contiguous M0 runs;
  after the gate `cp_async_wait()` in every issuing wave, then `__syncthreads()`; double-buffer (`GM_DBUF=2` fits at 256x256x64).
- Transposed B operand from row-major LDS (PV, V^T): `ds_read_b64_tr_b16`, two per bf16x8
  fragment; design the tile stride for 64 banks.
- Tile size: start at `IsaLevel::geometry()` (256x256x64, 2 buffers); for K <= ~2.5k try
  `-DGM_BM=192` measured through the interpreter, interleaved.
- Waves: 8-wave persistent objects must stay <=256 VGPR+AGPR (occ 2); a 4-wave object may use 512
  at occ 1. Set both launch_bounds and `amdgpu_waves_per_eu`.
- HBM-bound kernels: keep >=4 16-B loads in flight per lane; target 6200 GB/s, not 8000.
- Cross-workgroup sync: relaxed poll + one agent acquire; do not build on `PLOW_GATE_HIER`
  until pitfall 23's follower invalidate is fixed and stress-tested.
- Compute-bound estimates: 1660 TF/s bf16 sustained (MI350X; calibrate MI355X) for whole-GPU
  work, 4096 FLOP/clk/CU x actual clock for single-block screens.
- Any default flip for gfx950: re-run its goldens on gfx950 hardware; gfx942 results do not
  transfer (pitfall 18).
